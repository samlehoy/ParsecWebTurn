Experimental BUD test client (Windows x64)

The default is still WebRTC. The embedded WASM core and the MF/D3D11 video
and Opus audio paths remain in use. This test build additionally enables
GPU-only vendor-video acceleration for 8-bit HEVC: AMD AMF on AMD and direct
D3D11 Video on NVIDIA. H.264 and Intel/other GPUs retain Media Foundation.

Extract to a separate directory. Copy your existing settings.json into that
directory if you need your TURN settings; do not send that file to anyone.
Close other native ParsecWebTurn instances before starting this test client.
The normal protected account profile is reused; sign in if prompted.

Settings -> Experimental BUD (UDP only) -> Save settings.
Connect to a stock Parsec host using the normal computer picker.
BUD without Force TURN first tries direct UDP with STUN discovery. If the host
answers but direct connectivity fails (or has not established after 4 seconds),
the client makes one fresh BUD attempt through the first configured UDP TURN
endpoint. STUN-only mode disables this retry. Established streams are not
silently rerouted.
BUD with Force TURN selects the first configured UDP TURN endpoint. The
Cloudflare provider can generate temporary credentials as before.
BUD does not support TURN TCP/TLS and does not silently fall back to WebRTC.
Uncheck Experimental BUD, save and reconnect to return to WebRTC.

Check Connection stats: it must say experimental BUD, show actual codec,
resolution, the actual decoder and D3D11 decoder surface once playing.
Test H.264 first; then test HEVC if it already works on this GPU/driver.
Also check audio, cursor, immersive mode and disconnect/reconnect.

Connection stats uses native BUD counters: direct/relay route, BUD RTT, host
encode time when reported, AES-GCM, late fragments, duplicates, NACKs and
compressed-media backlog/drops. ICE candidates and DTLS are WebRTC-specific
and are hidden. Incoming/outgoing traffic measures UDP payload bytes, including BUD and TURN
protocol traffic; IP/UDP headers and account HTTPS/WSS traffic are excluded.

Direct and isolated UDP TURN connectivity and encrypted control delivery are
covered by automated tests. Stock-host direct and relay playback were confirmed
with the earlier test client. Please verify automatic TURN retry with Force TURN
OFF on the network where direct access fails, then Force TURN ON, and direct
access where available. Check disconnect/reconnect after each route.
Check Connection stats -> Decoder after enabling Prefer HEVC, saving and
reconnecting: AMD AMF HEVC or Direct D3D11 HEVC should appear on the matching
GPU. Both pass original GPU NV12 textures directly to the existing renderer.
A vendor error requests a keyframe and returns to MF for that connection;
Decoder fallback explains it. Please verify image colors/cropping, motion,
resolution changes and disconnect/reconnect on both AMD and NVIDIA.
This is an experimental test artifact. Only 8-bit 4:2:0 video is supported.
4:4:4 remains disabled. The default non-test build retains MF.

Experimental original-surface presentation (NVIDIA HEVC only):
Settings -> Zero copy (experimental, NVIDIA HEVC), select NVIDIA, enable
Prefer HEVC, Save settings and reconnect. Default is OFF. Both WebRTC and
BUD can use this GPU-only presentation option. Windows 11 and a compatible
WDDM 3.0 driver/decoder configuration are required. AMD, Intel and H.264
keep their existing renderer. The software UI overlay remains separate.
Connection stats shows the actual renderer and Zero copy status/fallback.
Original NV12 surfaces go directly to Windows Presentation API; the client
performs no intermediate frame copy or RGB conversion pass in this mode.
Windows can still compose the surface. Direct scanout is not claimed.
A support/lifetime/format error returns to the normal GPU renderer using
keyframe recovery; it never changes the selected network transport.
Please test colors/cropping, resizing/fullscreen, overlays, Settings/F8 and
repeated disconnect/reconnect. Uncheck the option to compare the normal path.
