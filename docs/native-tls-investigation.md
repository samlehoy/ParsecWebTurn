# Native TLS feasibility (2026-10-17)

This is a source/API investigation, not a TLS migration or a measured size or
latency result. Native TCP readiness and TLS provider selection are separate.

## Applicable connections

| Connection | Current implementation | Native TLS possibility |
| --- | --- | --- |
| HTTPS, updates, credentials | reqwest rustls feature | reqwest native-tls backend |
| Signaling WSS | tokio-tungstenite rustls feature | native-tls backend |
| WebRTC TURN/TLS | vendored ICE TurnStream + tokio-rustls | tokio-native-tls adapter; preserve framing, timers, cancellation and routing |
| BUD TURN/TLS | StreamIo + rustls | native_tls over the native TCP Read/Write adapter |
| WebRTC DTLS | dtls 0.13 | Keep DTLS: native-tls is not a replacement DTLS implementation |

The dtls dependency also uses rustls RootCertStore and WebPki verifiers (config.rs,
conn/mod.rs, handshaker.rs). Replacing the four TLS stream consumers does not
eliminate rustls/ring from the runtime graph. Rustls also appears in WebRTC's
certificate APIs. A graph reduction is not automatically a smaller executable:
Schannel wrapper code is added and unused Rust code may already be stripped.
Compare matched release builds and packaged ZIPs before stating a size saving.
Linux native-tls uses OpenSSL; Windows uses Schannel without an OpenSSL DLL.

## Behavioral equivalence

- Hostname/SNI, certificate expiry and chain validation: supported. Keep invalid
  certificate/hostname acceptance disabled and explicitly require TLS 1.2 or later.
- Trust roots: system roots and explicit private CAs are supported. The present
  union of WebPKI anchors and OS roots is not identical to OS trust. Retaining
  that precise union would require complete DER root certificates; the existing
  webpki-roots anchor structures cannot be passed as native_tls certificates.
- Nonblocking setup: preserve MidHandshakeTlsStream on WouldBlock and resume on
  native readiness, within the existing setup deadline and cancellation path.
- Backpressure and partial writes: retain the same TURN plaintext until its TLS
  write reports consumption. The Schannel implementation explicitly requires a
  retry with the same input after WouldBlock. Do not flush away a failed write's
  record and then retry that plaintext, which can encrypt/send it twice.
- Physical progress: observe completed TCP sends in the underlying adapter,
  rather than interpreting TLS plaintext consumption as wire progress. Keep the
  oldest output timestamp through partial writes and bound every wait by it.
- Pending output: combine an outstanding TLS operation/flush with native TCP's
  owned in-flight output. Do not consume another core datagram until both drain.
  TLS work generated by reads must also participate in tracking and deadlines.
- The exact rustls set_buffer_limit(32 KiB)/wants_write API has no native-tls
  equivalent. Bound application chunks and the native send buffer, preserve a
  single outstanding operation, and validate buffering under a blocked writer.
  An identical internal TLS memory ceiling cannot be promised via this API.
- Buffered input and fairness: buffered_read_size helps avoid sleeping with
  plaintext available; retain bounded read/write work and immediate continuation.
- Certificate validation follows OS policy on Windows. Its synchronous work is
  distinct from nonblocking socket I/O; a strict interruptible validation deadline
  is not established by native-tls's public API. Setup tests must cover this limit.

## Required acceptance before migration

Run the existing certificate rejection, private-CA, fragmented/burst stream,
partial-output age, idle control output, cancellation and coturn renewal tests
against the replacement. Add Schannel retry/flush tests proving exactly-once
plaintext delivery, bounded slow-writer buffering and no lost readiness wake.
Then validate HTTPS/WSS and WebRTC UDP/TCP/TLS independently. No decoder, GPU
surface, proprietary WASM, DTLS or SCTP changes are required by a TLS-only move.

The ordinary TLS uses can be unified with these adapters, but full behavioral
equivalence is not yet demonstrated by an implementation or test build.
